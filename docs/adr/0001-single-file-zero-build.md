# ADR 0001：继续使用单文件、零构建架构

- 状态：Accepted（临时）
- 日期：2026-11-21
- 决策人：项目发起人 + Claude

## 背景

产品最初为展览场景开发，要求一周内上线。当时只有 1–2 名开发者，选择了零构建、零服务器运维的方案：

- 前端：一个约 220KB 的 `index.html`，HTML/CSS/JS 全在里面；
- 后端：Cloudflare Pages 根目录的 `_worker.js`；
- 数据库：Supabase；
- 部署：手动上传文件夹到 Cloudflare Pages。

这套方案已经验证可用：线上域名正常、手机/电脑都能对话、数据库能写入。代码里有大量经过反复调试的细节（人设提示词、按天归档、洞察卡片、记忆召回、防重复发问等）。

## 决策

本轮继续使用单文件 + `_worker.js` + Cloudflare Pages，不迁移 React/Vue/Vite，不引入 bundler，不拆分 `index.html`。

工程化的范围限定在：

- Git / GitHub / Gitee 版本管理；
- GitHub Actions 自动部署；
- 本地 `wrangler pages dev` + mock 模式；
- README、CLAUDE.md、ADR、忽略规则和密钥管理；
- P0 隐私、明显 bug、埋点与体验打磨。

## 后果

**正面**

- 不重写，保留全部已调好的产品细节；
- 部署链路简单，回滚快；
- 线上域名和环境变量不动，风险最低；
- 本轮可以快速交付。

**负面**

- `index.html` 约 5400 行，定位和评审成本高；
- 无类型检查、无模块边界、难写单元测试；
- 多人同时改容易冲突；
- CSS/JS 重复代码只能靠人工发现。

## 重新评估的触发条件

满足任意两条即可考虑拆分或迁移：

1. 需要自动化测试（尤其是提示词解析、埋点、状态机）；
2. 同时开发的人超过 2 个；
3. `index.html` 超过 7000 行，或单次改动经常误伤其他功能；
4. 移动端性能出现明显问题；
5. 产品需要新增一整个功能模块（如兴趣小实验、情绪记录）。

## 未来迁移路径（如果触发）

1. 先把 CSS、JS、API client 抽成 `src/` 下的独立文件；
2. 用一个几十行的 Node 脚本拼成 `dist/index.html`，复制 `_worker.js`，部署方式不变；
3. 稳定后再评估 Vite + 框架；
4. 迁移过程中保持 API 契约 `{ code, message, data }` 和隐私边界不变。

> 注意：无论怎么拆，最终部署目录仍必须让 `_worker.js` 位于根部；不要使用 `functions/` 目录。
