## 0. 速览

### 0.1 一句话描述

「理想的自己」是一个 AI 陪伴式对话产品：用户完成 5 步自我画像设置后，与"五年后理想的自己"对话；每次「合上笔记本」，系统生成洞察卡片、识别行为模式，逐步沉淀成「日记本」和「模式地图」。

### 0.2 三条铁律（动代码前必读）

1. **不存聊天原文。** 用户与 AI 的对话只留在用户设备本地（localStorage），后端只收行为事件。隐私是本项目的产品底线，也是对外承诺。
2. **后端不要用 `functions/` 目录。** 已实测两次不被 Cloudflare 识别（`[[path]].js` 通配符版和按文件拆分版都失败），唯一稳定可用的是根目录 `_worker.js`。
3. **改完必须重新上传部署。** 本项目的"交付"不等于"生效"——文件给对方 ≠ 线上已更新。部署后必须走第 10.4 步验证，否则会出现"明明改了却没变化"。

## 1. 产品定义

### 1.1 定位

面向年轻人的「自我对话」产品。用"未来的自己"这个心理投射，降低自我剖析的门槛，让用户在低压力的对话中看见自己的模式。

### 1.2 核心体验闭环

```
进入页面 → 5 步画像设置 → 与"五年后的我"对话 → 合上笔记本
   → 生成洞察卡片 → 首次出现模式则弹留存反馈 → 沉淀到日记本/模式地图
```

### 1.3 要验证的三个假设（数据收集的出发点）

| 假设 | 对应指标 | 对应埋点 |
|---|---|---|
| 用户会深度对话 | ≥3 轮的会话占比 | `diary_closed` 的 `userTurns` |
| 模式识别能触达 | 看到洞察卡片/模式的人数比例 | `insight_card_shown`、`retention_feedback_shown` |
| 有留存意愿 | 反馈"会回来"的比例 | `retention_feedback_submitted` |

### 1.4 时间背景

展览场景，一周内需要上线并开始收集数据。因此技术选型刻意选择了**零构建、零服务器运维**的方案，任何方案都必须能在几小时内改完并部署。

### 1.5 完整用户漏斗（按埋点串联）

```
page_loaded
  → animation_complete
    → step3_complete → step4_complete → step5_complete → onboarding_complete
      → first_message_sent → message_sent ×N
        → diary_closed（含 userTurns）
          → insight_card_shown（含 cardType）
            → [首次模式] retention_feedback_shown → retention_feedback_submitted
              → pattern_map_opened → pattern_detail_viewed
```

## 2. 技术架构

### 2.1 架构图（文本版）

```
用户浏览器（手机 / 电脑）
  │  ① 加载页面 + 前端逻辑（localStorage 存对话/画像/模式）
  │  ② POST /api/session/init   → 建会话，拿 sessionId
  │  ③ POST /api/event          → 上报行为埋点
  │  ④ POST /api/chat           → 发消息，拿 AI 回复
  ▼
Cloudflare Pages 项目 ideal-self-chat
  ├─ 静态资源：index.html（env.ASSETS）
  └─ _worker.js（高级模式，接管 /api/*）
        ├─ REST 调 Supabase（service_role key）
        └─ HTTPS 调 DeepSeek（deepseek-chat）
  ▼
Supabase（新加坡节点）          DeepSeek API
  sessions / events / feedbacks     chat/completions
```

### 2.2 技术选型与理由

| 层 | 选型 | 为什么 |
|---|---|---|
| 前端 | 单文件 `index.html`（约 220KB，纯 HTML+CSS+JS，无构建） | 无打包步骤，改完直接上传；展览场景要快 |
| 托管 | Cloudflare Pages | 免费、国内可访问 `pages.dev`、支持上传部署 |
| 后端 | Pages 的 `_worker.js` 高级模式 | 与前端同域名，无跨域、无 `workers.dev` 国内不可达问题 |
| 数据库 | Supabase（新加坡节点） | 国内可直连、REST 调用简单、有 Web 控制台 |
| AI | DeepSeek `deepseek-chat` | 便宜、中文对话质量够用 |

### 2.3 关键约束（后续方案设计必须遵守）

- **国内网络可达性**：`pages.dev` 可访问，`workers.dev` 不稳定（曾直接 `ERR_CONNECTION_TIMED_OUT`）。任何后端都必须挂在 Pages 域名下。
- **零构建**：不要引入 webpack/vite/框架编译，除非同时解决"如何上传构建产物"。
- **单文件前端**：所有逻辑在一个 `index.html` 里，修改时注意搜索定位，不要假设有模块拆分。
- **API 额度**：DeepSeek 是按量付费/额度制，额度耗尽会表现为"页面能开、发消息一直转圈/失败"。

## 4. 后端 API 规格

### 4.1 统一响应格式

```json
{ "code": 0, "message": "success", "data": {...} }
```
- `code = 0` 表示成功；非 0 表示失败，`message` 为中文错误原因。
- 失败时 HTTP 状态码 400（`errorResponse`）或 500（chat 内部异常）。
- 健康检查返回 `{"code":0,"message":"服务运行正常","data":null}`。

### 4.2 接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api` 或 `/api/` | 健康检查 |
| POST | `/api/session/init` | 初始化会话 |
| POST | `/api/event` | 上报埋点 |
| POST | `/api/chat` | AI 对话 |

### 4.3 `POST /api/session/init`

请求：
```json
{ "channel": "default" }
```
（当前实现从 `?channel=` 取，默认 `"default"`；计划改为 `source`，见 12.2）

处理：生成 UUID → 写入 `sessions`：`session_id / channel / user_agent / ip_address`。

响应：`{ "code":0, "message":"会话初始化成功", "data":{ "sessionId":"..." } }`

> ⚠️ 注意：`sessionId` 只在初始化成功时返回。**若初始化失败，前端不写 localStorage，之后所有 `trackEvent` 会因 `sessionId` 为空而静默丢弃**——这是"埋点没数据"最常见的原因。

### 4.4 `POST /api/event`

请求：
```json
{ "sessionId": "uuid", "eventType": "page_loaded", "eventData": { "source": "douyin" } }
```
处理：`if (!sessionId || !eventType) return 400 缺少必要参数` → 写入 `events`：`session_id / event_name / event_params`。

> 前端字段名是 `eventType / eventData`，数据库字段是 `event_name / event_params`，映射在后端完成。改前端时不要想当然改后端字段。

### 4.5 `POST /api/chat`

请求：
```json
{ "sessionId": "uuid", "userInput": "今天好累", "messages": [ { "role":"system", ... }, { "role":"user", ... } ] }
```
处理：
1. 校验 `sessionId`、`userInput`；
2. `callDeepSeek`：`deepseek-chat`，`temperature 0.7`，`max_tokens 1000`；
3. **写 `feedbacks` 表（`session_id / user_input / ai_output`）—— 隐私风险，P0 待删除**；
4. 返回 `{ code:0, data:{ content:"..." } }`。

### 4.6 其他约定

- CORS：`Access-Control-Allow-Origin: *`（同域名部署后其实用不到，但保留无害）。
- IP：优先 `CF-Connecting-IP`。
- 未知 `/api/*` 路径：`404 接口不存在`。
- 非 `/api` 请求：交给 `env.ASSETS.fetch(request)` 返回静态文件。

## 5. 数据库设计（Supabase）

> 字段名以**后端代码实际写入的字段**为准；类型为建议值，核对时以 Supabase 控制台为准。

### 5.1 `sessions`（会话表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `session_id` | uuid / text | 主键，前端存 localStorage |
| `channel` | text | 当前实现写入（来源渠道） |
| `source` | text | **新增字段**，渠道来源（`?s=xxx`），待建 |
| `user_agent` | text | 浏览器 UA |
| `ip_address` | text | 客户端 IP |
| `created_at` | timestamptz | 默认 now() |

待执行 SQL：
```sql
ALTER TABLE sessions ADD COLUMN IF NOT EXISTS source TEXT DEFAULT 'direct';
CREATE INDEX IF NOT EXISTS idx_sessions_created_at ON sessions (created_at);
```

### 5.2 `events`（事件表，核心分析表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigserial / uuid | 自增或主键 |
| `session_id` | uuid / text | 关联会话 |
| `event_name` | text | 事件名，如 `diary_closed` |
| `event_params` | jsonb | 参数对象，如 `{"userTurns":3,"cardType":"ai_insight"}` |
| `created_at` | timestamptz | 默认 now() |

建议索引：
```sql
CREATE INDEX IF NOT EXISTS idx_events_name ON events (event_name);
CREATE INDEX IF NOT EXISTS idx_events_session ON events (session_id);
CREATE INDEX IF NOT EXISTS idx_events_created ON events (created_at);
```

### 5.3 `feedbacks`（聊天内容表）

- 结构：`session_id / user_input / ai_output / created_at`。
- **决策：停止写入**（保护隐私）。
- 处理建议：保留表结构不动（便于回滚与历史数据取证），后端删除写入代码；如需彻底合规，可清空历史数据。

### 5.4 字段命名对照（最容易踩的坑）

| 前端 | 后端 API 入参 | 数据库列 |
|---|---|---|
| `eventType` | `eventType` | `event_name` |
| `eventData` | `eventData` | `event_params` |
| `sessionId` | `sessionId` | `session_id` |
| `messageLength` | — | `event_params.messageLength` |
| `cardType` | — | `event_params.cardType` |
| `userTurns` | — | `event_params.userTurns` |

### 5.5 常用分析 SQL（放进 Supabase SQL Editor 即可跑）

**① 漏斗：各环节到达人数**
```sql
SELECT event_name, COUNT(DISTINCT session_id) AS users, COUNT(*) AS times
FROM events
GROUP BY event_name
ORDER BY users DESC;
```

**② 对话深度分布（核心假设 1）**
```sql
SELECT (event_params->>'userTurns')::int AS turns, COUNT(*) AS sessions
FROM events
WHERE event_name = 'diary_closed'
GROUP BY 1 ORDER BY 1;
```

**③ 洞察卡片类型分布（核心假设 2）**
```sql
SELECT event_params->>'cardType' AS card_type, COUNT(*) AS times
FROM events
WHERE event_name = 'insight_card_shown'
GROUP BY 1 ORDER BY 2 DESC;
```

**④ 留存意愿（核心假设 3）**
```sql
SELECT event_params->>'willingness' AS willingness, COUNT(*) AS n
FROM events
WHERE event_name = 'retention_feedback_submitted'
GROUP BY 1 ORDER BY 2 DESC;
```

**⑤ 渠道来源与转化**
```sql
SELECT s.source,
       COUNT(DISTINCT s.session_id) AS visitors,
       COUNT(DISTINCT e.session_id) FILTER (WHERE e.event_name = 'first_message_sent') AS chatters
FROM sessions s
LEFT JOIN events e ON e.session_id = s.session_id
GROUP BY 1 ORDER BY 2 DESC;
```

**⑥ 深度对话占比（≥3 轮）**
```sql
SELECT
  COUNT(*) FILTER (WHERE (event_params->>'userTurns')::int >= 3) AS deep_sessions,
  COUNT(*) AS total_sessions,
  ROUND(100.0 * COUNT(*) FILTER (WHERE (event_params->>'userTurns')::int >= 3) / NULLIF(COUNT(*),0), 1) AS deep_ratio_pct
FROM events WHERE event_name = 'diary_closed';
```

## 6. 隐私与数据边界（不可越界）

### 6.1 存什么 / 不存什么

| 数据 | 是否入库 | 说明 |
|---|---|---|
| 页面/步骤/点击行为 | ✅ 存 | events 表，无个人内容 |
| 对话轮次、卡片类型、模式名 | ✅ 存 | 属于行为统计，不含原文 |
| 用户主动提交的反馈文字 | ✅ 存 | 用户明确点击"发送"，属授权数据 |
| 留存反馈选择（会/犹豫） | ✅ 存 | |
| **用户与 AI 的对话原文** | ❌ **不入库** | 只留 localStorage |
| 画像内容（场景/痛点/性别/年龄） | ❌ 不入库 | 只在本地，用于生成提示词 |

### 6.2 风险点与整改

| 风险 | 现状 | 处理 |
|---|---|---|
| `feedbacks` 表存原文 | `_worker.js` 的 `handleChat` 仍在写 | **P0：删除该段写库逻辑** |
| 前端把 `feedbackContent` 全文上报 | `submitProfileFeedback` 里有 | 可保留（用户主动提交），但需明确告知用途 |
| localStorage 存对话原文 | 设备本地，不上传 | 属设计内；提供"清空历史"入口（已有 `clearAllHistory`） |

**实现要点（有坑，务必按这个来）**

- `diary_closed` 的 `userTurns` 必须在 `closeDiary` 里、**在 `clearCurrentConversation()` 之前**取，否则会拿到 0。
- `insight_card_shown` 有 4 种卡片渲染（见 8.4），`cardType` 要一一映射，不能只传一个固定值。
- `retention_feedback_shown` 只在 `localStorage.retentionFeedbackShown` 为空时触发（即首次模式），否则会重复上报。
- `animation_complete`：**当前版本没有独立开场动画**，只有 AI 回复的打字机动画（`triggerTextAnimation`）。若要保留此埋点，必须先定义"动画"指什么；否则建议改为 `intro_text_animated` 或直接砍掉。

### 7.4 旧埋点处置结论（取舍建议，待确认）

### 7.5 埋点验证清单（每次改完必跑）

1. 打开页面 → 看 Network 里 `/api/session/init` 是否 200 且返回 `sessionId`；
2. localStorage 里是否有 `sessionId`（没有 → 后续全部丢）；
3. 走一遍完整流程：设置 → 发消息 → 合上笔记本 → 关卡片；
4. Supabase 里 `SELECT event_name, COUNT(*) FROM events WHERE created_at > now() - interval '10 minutes' GROUP BY 1;`
5. 对应事件是否齐全、`event_params` 内容是否正确。

### 7.6 埋点常见坑

| 坑 | 后果 | 处理 |
|---|---|---|
| `sessionId` 为空 | 所有事件静默丢弃 | 初始化失败时重试，或允许无 session 上报 |
| `beforeunload` 里 `fetch` | 页面已卸载，请求可能被取消 | 用 `navigator.sendBeacon` 或 `fetch(..., {keepalive:true})` |
| `page_leave` 在手机上不触发 | 移动端切后台不走 `beforeunload` | 同时监听 `visibilitychange`（`document.hidden`） |
| 事件名改名但旧名残留 | 同一行为双份 | 全局搜索旧名，逐个替换 |
| 一次点击上报多次 | 数据虚高 | 检查事件是否绑在冒泡/循环里 |

## 8. 前端功能模块详解

### 8.1 引导流程（Onboarding，5 步）

| 步 | 标题 | 交互 | 产出字段 |
|---|---|---|---|
| 1 | 欢迎来到理想的自己 | 输入昵称（可选，≤10 字） | `nickname` |
| 2 | 选择你的核心特质 | 8 选 1 动物（老虎/豹子/大象/狐狸/狼/鹰/鹿/熊） | `animal`(emoji)、`animalName`、`trait` |
| 3 | 你的理想场景 | 文本框 | `scene` |
| 4 | 你的行动方向 | 多选动作 chips + 2 个痛点输入 | `actions`、`painPoint1`、`painPoint2` |
| 5 | 那现在的你呢？ | 性别 / 年龄段 / 状态 | `gender`、`ageRange`、`status` |

完成后写入 `localStorage.idealSelfProfile`，字段集合：
`animal, animalName, trait, scene, actions, painPoint1, painPoint2, gender, ageRange, status, nickname`。

- 首次完成 → 跳对话页并 `startFirstConversation()`；
- 编辑完成（`isEditing`）→ 回「理想的自己」页。

### 8.2 对话页与消息发送

- `sendMessage`：禁用按钮 → `trackEvent('submit_input')` → push 用户消息 → 清空输入 → `buildMemoryContext` 做**本地关键词召回**（从历史对话里找相关原话，纯本地，不上传）→ `chatWithAI` → 打字机输出。
- `chatWithAI` 只做一件事：POST `/api/chat`，失败抛错，由 `sendMessage` 捕获后 `trackEvent('network_error')` 并展示错误条。
- 开场白固定为「今天感觉怎么样？」，并且会写入 `conversationHistory`（避免 AI 重复发问）。
- 心情选择：8 个 emoji（开心/平静/低落/焦虑/烦躁/平淡/纠结/疲惫），可跳过。

### 8.3 「合上笔记本」`closeDiary`（最关键的分支）

```
userTurns = 当前对话中用户消息数
├─ userTurns < 3 → 存草稿 + 清空 + 显示"理想的我"卡片（鼓励型，引导继续聊）
└─ userTurns ≥ 3 → 调 finalizeConversation（AI 识别模式）
                    → 存 allConversations（含 messages 原文，仅本地）
                    → 有 insight → 洞察卡片
                    → hasPattern = (patternCount >= 2)
                    → 关闭卡片后：首次则弹留存反馈
```

### 8.4 洞察卡片：4 种渲染 → 3 类 cardType

| 触发场景 | 标题 | 建议 cardType |
|---|---|---|
| 聊了 <3 轮 | 「理想的我」+ 场景文本 | `encouragement`（或独立 `ideal_scene`） |
| 有 AI 洞察 | 「刚才的对话」+ insight | `ai_insight` |
| 有 highlight | 「这句话值得记住」 | `highlight` |
| 无洞察 | 「对话已收好」 | `encouragement` |

> 设计稿只定义了 3 类，但实际有 4 种渲染。落地时必须先定：`ideal_scene` 是否单列。建议单列，否则"短对话"会污染鼓励型的口径。

### 8.5 留存反馈（只在首次模式出现时弹）

- 触发条件：`handlePostInsight()` 中 `localStorage.retentionFeedbackShown` 不存在。
- 选项：`会` / 犹豫（二选一），选后追问文案不同（"是什么让你想回来？"/"是什么让你犹豫？"）。
- 提交后 `localStorage.retentionFeedbacks` 存一份（仅本地），并置 `retentionFeedbackShown=true`。
- 新埋点需要在 `showRetentionFeedback` 上报 shown、在 `submitRetentionFeedback` 上报 submitted（`willingness` = 选项原文）。

### 8.6 模式地图

- 8 个模式标签（必须是这 8 个之一，否则"无明显模式"）：
  拖延 / 自我攻击 / 焦虑 / 逃避 / 完美主义 / 内耗 / 讨好 / 情绪卡点。
- 识别时机：`diary_closed` 且 `userTurns ≥ 3`，由 `detectPatternWithAI` 调用 AI（8 标签单选 + 关键句 + highlights + 行动建议）。
- 展示阈值：**同一模式累计 ≥2 次才进地图**（`hasPattern = patternCount >= 2`），但每次识别都会存一条记录。
- 详情页反思文案会缓存到 `localStorage.patternReflections`，避免每次调 AI。

### 8.7 「理想的自己」页（profilePage）

- 展示画像：动物/trait/场景/行动/当前信息，可编辑（`editProfile`）。
- 常驻**反馈留言框**（`submitProfileFeedback`）：用户主动提交，是产品迭代最重要的定性数据来源。
- 工具条：分享、主题切换。

### 8.8 草稿自动保存

- 输入时写 `currentConversationDraft`（含消息、心情、最后活跃日）。
- `beforeunload` 与切页时保存；启动时 `handleDraftOnStartup` 判断是否跨天，跨天则 `autoFinalizeDraft` 归档。

### 8.9 localStorage 键清单（排查数据问题时对照）

| 键 | 内容 |
|---|---|
| `sessionId` | 会话 ID |
| `idealSelfProfile` | 用户画像 |
| `allConversations` | 全部日记（**含对话原文**） |
| `currentConversationDraft` | 当前草稿 |
| `detectedPatterns` | 识别到的模式记录 |
| `patternReflections` | 模式反思缓存 |
| `retentionFeedbacks` | 留存反馈（本地） |
| `retentionFeedbackShown` | 是否已弹过 |
| `userFeedbacks` | 页面反馈（本地） |
| `theme` | 深浅色 |

### 8.10 系统提示词机制（`generateSystemPrompt`）

动态拼接，核心结构：
1. **身份**：我是五年后的你（`now.getFullYear()+5`）；
2. **时间锚点**：写入"今天是 X 年 X 月 X 日 星期X"，解决"今天/昨晚"的指代；
3. **理想状态**：由 profile 的场景/动物/trait/actions 生成；
4. **潜意识/痛点**：painPoint 生成，并附"不要主动刺痛我"的禁忌条款；
5. **表达哲学**：不说教、不评判、短句、可少量 emoji。

> ⚠️ 已知问题：后端 `callDeepSeek` 又**额外拼了一个固定 system prompt**，导致每次请求有两条 system 消息。DeepSeek 通常以后出现的为准，但这是隐性风险（前端画像可能被稀释）。建议后端删掉固定 prompt，只保留前端动态 prompt。

## 9. AI 提示词与调用参数

| 用途 | 位置 | 模型/参数 |
|---|---|---|
| 主对话 | 前端 `generateSystemPrompt` + 后端 `callDeepSeek` | `deepseek-chat`，`temperature 0.7`，`max_tokens 1000` |
| 模式识别 | 前端 `detectPatternWithAI` | 同模型，要求严格返回 8 标签之一 + JSON |
| 洞察生成 | 前端 `finalizeConversation` 链路 | 生成一句 `insight` |
| 反思文案 | `generateAndCacheReflection` | 生成后缓存，减少调用 |

**调优注意**
- `max_tokens 1000` 对长回复可能截断，若用户反馈"话说一半"，先调这个。
- 模式识别 prompt 是"医生诊断"风格（症状导向、区分主语、单选标签），改动时不要删掉"必须从 8 个标签中选 1 个"，否则会返回自由文本导致解析失败。
- 所有 AI 调用都在前端发起、经后端转发；后端只加 key，不存内容。

2. Pages 项目 → **Create deployment** → 上传文件夹 → **Deploy site**；

| 步骤 | 操作 | 预期 |
|---|---|---|

| 2 | 打开首页发一条消息 | 有 AI 回复 |
| 3 | Supabase 查最近 10 分钟 events | 有新记录 |
| 4 | 手机（不挂代理）打开主域名发消息 | 正常回复 |

### 10.5 两个域名的差别（分享用哪个）

| 类型 | 示例 | 行为 | 用途 |
|---|---|---|---|
| 主域名（Domains） | `ideal-self-chat.pages.dev` | 永远指向**最新**部署 | **对外分享用这个** |
| 部署域名（Deployments） | `<hash>.ideal-self-chat.pages.dev` | 指向**某一次**部署，后续更新不影响它 | 回滚、对比历史版本 |

### 10.6 回滚

Deployments 列表里选上一个正常版本 → 「Rollback to this deployment」。回滚只回滚静态资源和 `_worker.js`，**不回滚环境变量**。

### 10.7 常见部署误区

- 把 zip 直接上传（Cloudflare 只认解压后的文件夹内容）；
- 上传了外层目录（导致 `index.html` 不在根，首页 404）；
- 改了代码但没重新 Deploy，只在本地看。

## 11. 故障排查手册（真实踩坑记录）

| 现象 | 真实根因 | 解决 |
|---|---|---|
| 页面能打开，发消息一直转圈 / `Failed to fetch` | 后端在 `workers.dev`，国内不通（`ERR_CONNECTION_TIMED_OUT`） | 迁到 Pages `_worker.js`，同域名 |
| 提示"返回的不是有效的 JSON" | 访问 `/api` 返回的是前端 HTML（Functions 未生效）→ `res.json()` 解析失败 | 确认 `_worker.js` 被识别（10.3 第 3 步） |
| Functions 标签页是介绍页 | `functions/` 目录未被识别（试过 `[[path]].js` 与拆分文件两种都失败） | 改用根目录 `_worker.js` |
| 报"缺少必要参数: sessionId 或 eventType" | 前端 `sessionId` 为空（初始化失败或清过缓存） | 检查 `/api/session/init` 返回；刷新后重试 |
| 电脑能聊、手机不能 | 手机未挂代理，访问不了旧 Worker 域名 | 同上，同域名方案 |
| 部署完还是旧页面 | 浏览器缓存 / 部署未完成 | 强制刷新；确认部署时间戳 |
| 数据库没数据 | 环境变量没配对 / 表名错 / RLS 拦截 | 看 Worker 日志（`console.error` 已打印 Supabase 状态码） |
| 额度问题：白天能用晚上不行 | DeepSeek 额度耗尽/限流 | 充值或换 key；前端会报 `AI 服务异常: 4xx` |

**排查顺序（照这个走最快）**
1. 浏览器直开 `/api` → 判断后端活没活；
2. F12 Network 看 `/api/chat` 的状态码与响应体；
3. 看 localStorage 有没有 `sessionId`；
4. Supabase 里查 events 有没有新记录；
5. Cloudflare 部署详情 → Functions 是否识别。

- 交付物 = **可直接上传的文件夹**（`index.html` + `_worker.js`），不是代码片段、不是说明文字。
- 每次交付必须同时给出：改了哪几处、对应行号/函数、部署后怎么验证。
- 不要声称"已修改完成"却不给文件；不要声称"已上线"却没验证。

### 14.3 命名与风格

- 埋点：`名词_过去式`；参数 camelCase。
- 前端函数：动词开头（`show*` / `load*` / `handle*` / `generate*`）。
- 数据库列：snake_case。
- 中文文案：第二人称、短句、不评判、不说教（与产品调性一致）。

### 14.4 绝对不要做

- ❌ 把用户对话原文写入数据库（包括"为了调试方便"）。
- ❌ 把 API Key / service_role key 写进前端或文档。
- ❌ 用 `functions/` 目录做后端。
- ❌ 只改文件不重新部署，然后说"已生效"。
- ❌ 在同一个行为上同时保留新旧两个事件名。
