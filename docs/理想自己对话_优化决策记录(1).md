### 2026-06-22 · 后端部署方案：从 Workers 独立域名改为 `_worker.js` 同域部署 ✅ 已实现

**背景 / 问题**

产品上线展览后出现了一个严重问题：**手机打不开，只有挂节点的电脑能用。**

排查后发现，前端和后端是两个不同的域名：

| 组件 | 域名 | 国内访问 |
|---|---|---|
| 前端页面 | `ideal-self-chat.pages.dev` | ✅ 正常（Cloudflare Pages 域名在国内能访问） |
| 后端 API | `ideal-self-api.nuranisajudda.workers.dev` | ❌ 不稳定，经常访问不了 |

因为在 `.workers.dev` 这个域名下，国内网络对它不稳定，经常直接访问不到。所以：

- **电脑 + 挂节点** → 网络层面绕过了限制 → ✅ 正常对话
- **手机（没挂节点）** → 前端页面能打开（Pages 域名），但发消息时调不到 Worker API → ❌ 一直加载不回复
- **旧版本链接** → 打开就报参数缺失（那是旧代码自己的问题，和网络无关）

根本矛盾：**页面能打开，但发消息没反应**——因为页面是 Pages 加载的，API 请求却要走另一个被墙的域名。

**决策：用 `_worker.js` 单文件模式，让前后端共用一个域名**

改完之后：

| | 改之前 | 改之后 |
|------|-----------------------------|----------------------------|
| 前端 | `ideal-self-chat.pages.dev` | `ideal-self-chat.pages.dev` |
| 后端 API | `ideal-self-api.xxx.workers.dev`（另一个域名） | `ideal-self-chat.pages.dev/api/chat`（同一个域名！） |
| 手机能用吗 | ❌ | ✅ |
| 需要挂节点 | 需要 | 不需要 |
| 跨域问题 | 有 | 没有 |

**尝试过的方案**

**方案一：Pages Functions `functions/` 目录（文件路由）** ❌ 未被识别

用 `functions/api/chat.js` 这种文件路由方式部署后，Cloudflare 的 Functions 标签页仍然是"介绍页面"——没有被识别到任何函数。原因可能是 Pages 版本或配置问题。

**方案二（最终采用）：`_worker.js` 单文件高级模式** ✅

这是 Cloudflare Pages 的"高级模式"：在项目根目录放一个 `_worker.js` 文件，这个文件接管所有请求——包括前端静态文件和后端 API 逻辑。写法和原来的 Worker 完全一样。

项目结构变得极简：

```
ideal-self-v3/
├── index.html      ← 前端页面（全部逻辑在这一个文件里）
└── _worker.js      ← 后端逻辑（就这一个文件，处理所有请求）
```

**`_worker.js` 的处理逻辑**：

- 请求 `/api/chat` → 走 AI 对话逻辑（和原来的 Worker 一模一样）
- 请求 `/api` → 返回 `{"code":0, "message":"服务运行正常"}`（健康检查）
- 其它所有请求 → 返回 `index.html`（前端页面）

关键点：`_worker.js` 会接管所有请求，所以**必须显式处理静态文件**——否则用户打开页面看到的也是 Worker 返回的内容而不是前端页面。做法就是：API 路由以外的请求，全部返回 `index.html`。

**验证步骤**

部署后依次检查：

1. **Functions 标签页**：进入部署详情 → Functions 标签 → 应该能看到 `_worker.js` 函数（不再是"介绍页面"）
2. **后端健康检查**：浏览器打开 `https://ideal-self-chat.pages.dev/api` → 应显示 `{"code":0,"message":"服务运行正常"}`
3. **完整功能测试**：打开首页 → 发一条消息 → 看能不能收到 AI 回复
4. **Supabase 数据验证**：去 Supabase 看三张表（对话记录、模式、埋点）有没有新数据写入

**为什么这样做**

1. **一劳永逸**：同一个域名下，只要能打开页面就一定能发消息——不存在"页面能看但功能不能用"的割裂
2. **不需要挂节点**：Pages 域名本身国内可访问，API 搭在上面也一样可访问
3. **零额外成本**：Pages Functions 和 Workers 一样有免费额度，MVP 阶段完全够用
4. **代码写法不变**：`_worker.js` 里的路由逻辑、API 调用、Supabase 写入、埋点记录，全部和原来的 Worker 一模一样——只是换了个部署位置
5. **Supabase 不受影响**：数据表、埋点、AI 功能全部保持不变（后端逻辑没变，只是域名换了）

**为什么不用 `functions/` 目录模式**

`functions/` 的文件路由模式理论上更"正规"（按目录结构自动映射路由），但这次部署后 Cloudflare 没有识别到。`_worker.js` 是更基础、更稳定的模式，本质就是一个 Worker 跑在 Pages 上——和原来独立 Worker 的写法 100% 兼容，出问题的概率最低。

**涉及的概念（小白笔记）**

- **Workers vs Pages Functions**：两者本质上是一样的（都是跑在 Cloudflare 边缘节点的 JS 代码），区别只在于部署方式。独立 Worker = 自己的域名（`.workers.dev`）；Pages Functions = 挂在 Pages 项目域名下。
- **`_worker.js` 高级模式**：Cloudflare Pages 的一种模式，用一个文件处理所有后端逻辑 + 静态文件分发。比 `functions/` 目录模式更底层、更灵活。
- **同域部署**：前端页面和后端 API 在同一个域名下，浏览器不会因为"不同源"而拦截请求，也不需要挂节点——对用户来说就是一个普通的网站。
- **域名被墙 / 网络不稳定**：某些境外域名在国内网络环境下访问不稳定或完全无法访问，这是物理层面的限制，代码写得再好也解决不了——只能通过换域名来解决。

- 展览一周内需要上线，需要收集用户数据验证核心假设
- 关键假设：用户会深度对话、模式识别能触达、有留存意愿
- 当前状态：localStorage 本地存储，看不到整体数据

**决策：13个埋点 + Supabase后端**

**核心埋点设计（按用户路径）**：
1. `page_loaded`：各渠道进入量（带 `source` 参数）
2. `animation_complete`：动画完播率
3-5. `step3/4/5_complete`：设置漏斗
6. `onboarding_complete`：完成设置率
7. `first_message_sent`：真正开始对话的人数
8. `diary_closed`：对话轮次分布（记录 `userTurns` 可以是1、2、3...任意值）
9. `insight_card_shown`：卡片类型分布（每次合上笔记本必然触发）
10. `retention_feedback_shown`：首次模式触发（仅第一次模式识别时）
11. `retention_feedback_submitted`：留存意愿
12-13. `pattern_map_opened` / `pattern_detail_viewed`：地图使用率

**关键说明**：
- 埋点8（`diary_closed`）：用户每次点"合上笔记本"都会触发，不管聊了几轮。`userTurns` 记录实际轮次，用于分析对话深度分布
- 埋点9（`insight_card_shown`）：每次合上笔记本都会弹卡片，`cardType` 区分三种类型（`ai_insight` / `highlight` / `encouragement`）
- 埋点10（`retention_feedback_shown`）：只在**第一次模式识别**时触发（同一模式累计≥2次），后续不再弹

**为什么这样设计**：
- 能回答核心问题：多少人深度对话（≥3轮）？洞察触达率？模式识别触达率？
- 漏斗清晰：从进入页面 → 完成设置 → 发消息 → 深度对话 → 看到价值
- 轻量级：13个埋点覆盖关键路径，不过度埋点

**技术方案**：
- 后端：Cloudflare Workers 代理 API + 记录埋点
- 数据库：Supabase（新加坡节点，中国可访问）
- 多渠道追踪：URL 参数 `?s=xxx` 区分来源

### 2026-06-21 · 用户身份字段注入系统提示词 ✅ 已实现（v3）

**背景 / 问题**
- AI 不知道用户性别，导致代词错误（女生被当成男生，喜欢的对象性别推断错误）
- AI 不知道用户年龄和状态，无法准确共情生活场景

**决策：性别、年龄范围、目前状态 → 动态注入系统提示词**

**实现方式**：
在"核心身份"部分拼接自然语言：
```
你是我，只是更完整的那个版本——来自五年后的2031年。现在的我，是一个25-30岁的女生，正在职场打拼。
```

**生成逻辑**：
- 性别 → "男生" / "女生"
- 年龄范围 → 直接使用（如"25-30岁"）
- 状态映射：
  - 上学 → "还在上学"
  - 上班 → "正在职场打拼"
  - 自由职业 → "做自由职业"
  - Gap → "在间隙期"
  - 其他 → "在探索自己的路"

**为什么这样做**：
- AI 需要这些信息来正确使用代词（他/她）
- AI 需要理解用户生活场景（上学的人不会说"辞职"，Gap的人更可能谈迷茫）
- 自然语言形式，不会让提示词显得生硬

### 2026-06-20 · 洞察小卡片：解决"第一次对话无即时价值"问题 ✅ 已实现（v3）

**背景 / 问题**
- 核心矛盾：产品是"长期看见模式"的工具，但"模式"需要 2-3 次重复才显现
- 导致：用户第一次对话结束 → 模式地图还是空的 → 没有"啊哈时刻" → 不想第二次打开
- 当前流程：对话结束直接回首页，**没有任何即时反馈**

**讨论过的方案（都否决了）**
- ❌ 加冥想/正念功能：分散核心价值，做浅没用、做深来不及
- ❌ 话术模板化（"你提到拖延，可能和拖延有关"）：空洞，用户自己都知道是拖延

**关键洞察：标签识别 vs 洞察生成是两件事**
| 维度 | 标签识别 | 洞察生成 |
|---|---|---|
| 目的 | 统计重复，构建模式地图 | 即时反馈，AHA moment |
| 约束 | 必须8选1（固定标签） | 自由发挥，可超越标签 |
| 优先级 | 找表面症状（容易统计） | 找深层原因（最有洞察感） |
| 用户感知 | 看不到（count≥2才显示） | 每次都看到（弹卡片） |
- 类比：标签=医生诊断病名（病历记录），洞察=医生叮嘱原因（让患者理解）
- 两者**松耦合**：洞察知道标签是什么，但不被它限制

**决策：每次对话结束弹"洞察小卡片"**

1. **洞察由 AI 生成，不依赖标签**：
   - 在现有的 `detectPatternWithAI` 里加一个 `insight` 字段（任务2）
   - 要求：不重复用户已知的（不说"你拖延了"），指出没意识到的（语气、用词、深层机制）
   - 例："你用'又'这个字，说明你已经注意到了重复。拖延背后，可能是害怕做不好。"

2. **成本极低**：复用现有 API 调用，只多返回一个字段（~50 tokens，增加约2%）
   - 关键认知：API 成本主要在输入 prompt（~2000 tokens），多返回1-2句话几乎不增加成本
   - 对比：新开一次独立 API 调用要重发对话内容，成本增加25%——所以选"同一调用多返回"

3. **卡片分四种情况**（根据识别结果动态选）：
   | 情况 | 卡片类型 | 内容 |
   |---|---|---|
   | 有 insight | 洞察型 | AI 生成的深层观察 |
   | 无 insight 但有正向亮点 | 金句回放 | "这句话值得记住：你的原话" |
   | 对话<3轮 | 鼓励型 | "理想的你XX，而此刻在路上" |
   | 啥都没有 | 温和收尾 | "把话说出来本身就是疗愈" |

4. **count≥2 时**，卡片多一个"去模式地图看看"按钮（引导查看汇总）

**UI：卡片翻转动画（符合纸质日记调性）**
- 入场：从下方浮起
- 自动翻转：正面（空白便签+icon+"轻触翻开"）→ 背面（洞察内容）
- 纸张质感：`#F5F1E8` 底色 + 纹理 + 霞鹜文楷

**触发时机的边界处理**
| 场景 | 弹卡片？ | 理由 |
|---|---|---|
| 点"合上笔记本"（<3轮） | ✅ 鼓励型 | 即时反馈 |
| 点"合上笔记本"（≥3轮） | ✅ 洞察型 | 即时反馈 |
| 切换页面（自动存草稿） | ❌ | 用户还在用，不打断 |
| 跨天自动收尾（后台） | ❌ | 对话是昨天的，今天弹出时间错位；改用温和提示（待实现） |

**和模式识别会不会打架？**
- 不会，是串行的：识别 → 显示卡片 → 关闭卡片 → 跳转首页
- 识别逻辑（`finalizeConversation`）完全不变，只是让它返回结果供卡片使用

**技术实现**
- `detectPatternWithAI` prompt：新增"任务2：生成即时洞察"，JSON 加 `insight` 字段
- `finalizeConversation`：返回 `{pattern, insight, highlights, patternCount}`
- 新增 `showInsightCard(options)`：卡片翻转动画 + 事件处理
- 新增 CSS：`.insight-overlay/.insight-card/.insight-face` 等（翻转+纸质感）
- 新增 `PATTERN_ICON` 映射
- 改 `closeDiary()`：识别后根据结果显示对应卡片

**涉及的概念（小白笔记）**
- **AHA moment**：让用户瞬间感受到价值的时刻（"原来如此！""它懂我！"）—— 和"用户反馈"不是一回事
- **松耦合**：两个功能互相参考但不互相绑死，各自能独立调整
- **API 成本结构**：成本大头在输入，输出多写几句几乎不花钱——所以优先"一次调用多返回"而非"多次调用"

**现状 / 下一步**
- ✅ 已实现：洞察卡片完整功能 + 翻转动画 + 四种情况
- ✅ 语法检查通过
- ⏳ 待测试：实际对话验证 insight 质量、卡片动画效果
- ⏳ 待实现（可选）：跨天自动收尾时的温和提示（"昨天的对话已自动保存"）

### 2026-06-19 · 时间线 bug 修复：统一"五年后" + 动态年份 + 未来身份锚点 ✅ 已实现（v3）

**背景 / 问题**
- 用户没设置"几年后的理想自己"，AI 却突然说"我这里也是2026年"
- 根本原因：system prompt 只有"今天是2026年"的日期锚点，没有"你来自未来"的身份锚点
- AI 不知道自己站在未来，当用户说"我这里也是2026年"，它就懵了，顺着确认

**决策：统一设成"五年后"，不让用户选**
- 理由1：选"3年后"还是"5年后"对 AI 回复几乎没区别，反而造成选择负担
- 理由2：引导流程已经够长，不加步骤
- 理由3：5年是"够远能成长、又不至于虚无缥缈"的甜蜜点；引导流程文案本就写"五年后的你"

**实现：动态算年份 + 未来身份锚点**
```javascript
const futureYear = now.getFullYear() + 5; // 动态算，不写死
// system prompt 加：
// "你是我，只是更完整的那个版本——来自五年后的${futureYear}年。"
// "对你而言，现在（2026年）的这些挣扎都已经走过了。但当我们对话时，你回到此刻陪我——
//  所以你知道'今天'是${todayStr}，也记得未来的你是什么样子。"
```
- 动态算年份（不写死2031），和之前的日期锚点设计一致

**现状 / 下一步**
- ✅ 已实现：AI 现在知道"我活在2031，但此刻回到2026陪你"

### 2026-06-19 · 开场白丢失 bug 修复：AI 重复发问 / 上下文不完整 ✅ 已实现（v3）

**背景 / 问题**
- 现象：手机上 AI 说完开场白"今天感觉怎么样？"，用户回"hi"，AI 又重复问了一遍"今天感觉怎么样？"
- 用户困惑：手机上 AI 回复"比较弱智"，电脑上正常——但 HTML 文件、profile、开场白都一模一样

**排查过程**
1. 先排除"假对比"：手机和电脑 localStorage 独立，且两次问的问题不同（手机问了元问题"什么叫跑的是你"，逼 AI 跳出人设）
2. 控制台验证 `conversationHistory` 和 `currentConversation`：
   - `currentConversation` 里有开场白（界面显示用）
   - `conversationHistory` 里**只有 system prompt，没有开场白**（这是发给 API 的真正历史）

**根本原因**
- 开场白通过 `addTypingMessage('今天感觉怎么样？', false)` 显示，这个函数**只 push 到 `currentConversation`，没 push 到 `conversationHistory`**
- 两个数组分工：
  - `currentConversation` = 界面显示 + 草稿保存
  - `conversationHistory` = **真正发给 API 的对话历史**
- 结果：用户回"hi"时，AI 收到的历史是 `[system][user:hi]`，看不到自己说过开场白
- system prompt 又让它"开场说今天感觉怎么样"，于是它以为还没开场，**重复发问**

**为什么手机重复、电脑不重复**
- 纯模型随机性（`temperature: 0.6`）。同样缺上下文，模型有时重复开场（手机那次），有时顺着"hi"往下走（电脑那次）
- 用户感觉的"手机更弱智"本质是 bug 导致的上下文不完整，不是平台差异

**修复**
1. `startNewConversation()` 和 `startFirstConversation()` 里，开场白显示后同步 push 到 `conversationHistory`：
   ```javascript
   const openingLine = '今天感觉怎么样？';
   addTypingMessage(openingLine, false);
   conversationHistory.push({ role: "assistant", content: openingLine });
   ```
2. 附带修复：`startFirstConversation()` 里重新生成 system prompt（用户刚填完 profile，旧的 conversationHistory 是页面加载时初始化的，system prompt 缺动态部分）

**涉及的概念（小白笔记）**
- **双数组分离的陷阱**：界面显示数组和 API 历史数组分开维护，容易出现"界面有、API 没有"的不一致
- **race condition 的误判**：表面像是"手机性能问题"，实际是数据缺失 + 模型随机性的叠加

**现状 / 下一步**
- ✅ 已实现：开场白同步进入 conversationHistory
- ✅ 已实现：首次对话重新生成 system prompt
- ✅ 语法检查通过

### 2026-06-19 · System Prompt 人设弱化问题修复：恢复"潜意识痛点"+ 优化动态生成 ✅ 已实现（v3）

### 2026-06-18 · 记忆召回失忆bug修复 + 状态重置问题 ✅ 已实现

**背景 / 问题1：记忆召回"失忆"**
- 用户场景：AI 提到"你面试客户总监"，用户问"你什么时候知道的"，AI 先引用了记忆（6月3日的记录），但用户换个问法"你能搜索出来吗？"，AI 却说"里面没有提过客户总监的事"
- 根本原因：记忆召回逻辑每轮独立触发，只看用户**当前这一句话**的关键词，不看本次对话的上下文
- 荒谬之处：同一次对话里，AI 刚刚引用过的记忆，下一轮就"忘了"

**问题2：草稿恢复后无法对话**
- 表现：刷新页面后，对话页显示"这是历史对话，想继续聊天？返回首页..."，输入框被禁用
- 控制台状态：`isViewingHistory: true`，`currentConversation.length: 49`，草稿不存在
- 原因：用户之前查看过历史对话（`isViewingHistory = true`），刷新后恢复草稿时，这个标志没有被重置

**决策**

**修复1：记忆召回使用本次对话上下文**
- `recallFromHistory()` 新增 `recentContext` 参数，接受本次对话最近5轮的消息（包括AI和用户说的话）
- 从这些消息中提取关键词，合并到当前消息的关键词中，一起用于召回
- 效果：即使用户换个问法（"你能搜索出来吗"），因为前几轮有"客户总监"，也能继续召回到相关记忆

```javascript
// 调用处
const recentMessages = currentConversation.slice(-5);  // 最近5轮
const memoryContext = buildMemoryContext(message, recentMessages);
```

**修复2：恢复草稿时重置 isViewingHistory**
- `restoreDraftConversation()` 里明确添加 `isViewingHistory = false`
- 确保恢复草稿后，用户处于"正常对话模式"而非"查看历史模式"

**为什么这样设计**
1. **上下文窗口合理**：最近5轮（约10条消息）足够捕捉当前话题，不会引入太多噪音
2. **符合对话直觉**：用户认为"我们正在聊这个话题"，AI 应该记得前几轮提到的关键词
3. **状态明确性**：草稿 = 可继续的对话，历史 = 只读的归档，两者不能混淆

**技术细节**
- `currentConversation` 是界面层的消息数组，包含 `{text, isUser}` 对象
- 用 `slice(-5)` 取最近5轮，传给 `recallFromHistory()` 作为额外的关键词来源
- `isViewingHistory` 是全局标志，控制输入框是否禁用

**涉及的概念**
- **上下文窗口**：记忆召回时考虑的对话范围，太短容易失忆，太长引入噪音
- **状态重置**：页面刷新后，某些状态（如 `isViewingHistory`）应该从持久化数据（草稿）重新推断，而不是保留上次的值

- ✅ 已实现：记忆召回使用5轮上下文
- ✅ 已实现：草稿恢复时重置 `isViewingHistory`

### 2026-06-18 · 对话收尾逻辑重构：从「按句数」改为「按天归档」 ✅ 已实现

**背景 / 问题**
- 之前的逻辑：页面内切换时，≥3 句就自动收尾并清空对话
- 用户反馈：聊到一半切到模式地图看看，再回来想继续聊，对话却没了，开了新对话
- 根本矛盾：决策记录说"页面内切换→对话保留"，代码却在收尾
- 阈值混乱：决策记录写10句，注释写10句，代码常量是3句

**之前逻辑的弊端**
1. **按句数收尾不直观**：用户不会数自己说了几句，"我到底说够没说够？"
2. **页面切换误触收尾**：刚聊3句切个页面就被收尾，体验割裂
3. **长对话被强行打断**：聊得投入，超过10句就被收尾，用户可能还想继续
4. **不符合日记本隐喻**：日记本是"一天一页"，不是"够10句一页"

**决策：改为「一天一页日记本」**
- **核心原则**：对话归属于最后活跃的那一天，跨天后自动归档
- **"今天"的定义**：自然日 00:00-23:59（未来可调整为"凌晨4点到第二天凌晨4点"给深夜用户缓冲）
- **跨天判断时机**：只在用户离开后重新回来时判断，不在正聊时打断

**三种场景行为**

| 场景 | 触发时机 | 行为 |
|---|---|---|
| **页面内切换** | 点导航栏切走 | 保存草稿（更新 `lastActiveDate`）<br>对话保留，不收尾<br>切回来时判断是否跨天 |
| **合上笔记本** | 点右上角按钮 | 立即收尾归档到当天<br>触发模式识别<br>跳转首页 |
| **关闭网页/超时** | 关闭标签/20分钟无操作 | 保存草稿（更新 `lastActiveDate`）<br>下次启动时判断是否跨天 |

**跨天判断逻辑**
```javascript
// 保存草稿时
草稿 = {
    messages: [...],
    mood: '😊',
    lastActiveDate: '2026-06-06',  // 最后一次在对话页活跃的日期
    timestamp: '...'
}

// 回到对话页 / 启动时检测
if (草稿.lastActiveDate !== 今天) {
    // 跨天了 → 收尾归档到 lastActiveDate
    收尾(草稿, 归档日期=草稿.lastActiveDate);
} else {
    // 还是今天 → 恢复继续聊
    恢复草稿();
}
```

**关键场景举例**

**场景A：聊到过12点，没离开**
- 11:30 PM 开始聊 → 12:30 AM 还在聊
- ✅ 不触发判断，继续聊
- 1:00 AM 切到模式地图 → 保存草稿，`lastActiveDate = "6月7日"`
- 1:05 AM 切回对话页 → 还是6月7日，继续聊

**场景B：聊完离开，第二天回来**
- 6月6日 11:30 PM 聊完，切到首页 → 保存草稿，`lastActiveDate = "6月6日"`
- 6月7日 9:00 AM 切回对话页 → 检测到跨天 → 收尾归档到6月6日 → 开新对话

**场景C：聊完关闭网页，第二天打开**
- 6月6日 11:30 PM 聊完，关闭网页 → 保存草稿
- 6月7日 9:00 AM 打开 App → `handleDraftOnStartup()` 检测到跨天 → 收尾归档到6月6日

**为什么这样设计**
1. **符合日记本隐喻**：日记本就是"一天一页"，不是"够N句一页"
2. **用户心智模型自然**："今天还没聊完" vs "我说了几句？"
3. **不会误触收尾**：当天内随时能续聊，页面切换不会打断
4. **长对话不受限**：今天想聊多久聊多久，不会被"够10句"打断
5. **归档时间清晰**：11点聊到凌晨1点 → 归档到"第二天"（符合用户认知"昨晚聊到很晚"）

**技术优势**
- **Token消耗更少**：删掉了"页面切换误触收尾"的浪费
- **代码更简单**：只判断日期字符串，不需要数句子
- **逻辑更清晰**：删掉 `AUTO_FINALIZE_TURNS` 常量，没有阈值混乱

**代码改动位置**
1. `autoSaveCurrentConversation()` - 保存时加 `lastActiveDate`
2. `switchPage()` - 删掉 `if (userTurns >= 3)` 自动收尾，只调 `autoSaveCurrentConversation()`
3. `handleDraftOnStartup()` - 改成判断 `lastActiveDate !== 今天`
4. 切回对话页时 - 加跨天判断逻辑
5. `finalizeConversation()` - 接受 `archiveDate` 参数，归档到指定日期

**涉及的概念（小白笔记）**
- **lastActiveDate**：对话最后一次活跃的日期，用于判断是否跨天
- **归档日期 vs 开始日期**：对话归档到最后活跃日，不是开始日（11点聊到1点→归档到第二天）
- **跨天判断时机**：只在"离开后回来"时判断，不在正聊时打断

- ✅ 已实现：完整的跨天判断逻辑
- 历史决策记录已更新，标注了旧逻辑的弊端

### 2026-06-06 · 正向亮点 summary 优化：从「清单」到「一击」 ✅ 已实现

**背景 / 问题**
- AI 提炼的 summary 变成"你A，也B，同时C"的罗列式长句
- summary 有时比原话还长（如：原话6字，summary 30+字）
- sources 放了3句，summary 就试图覆盖3个点

**根本原因**
AI 误解了 sources 和 summary 的关系，以为"sources 有几条，summary 就得讲几条"

**决策**
明确 sources 和 summary 的分工：
- **sources**：追溯线索（宽），把所有相关原话都放进来
- **summary**：一句话洞察（窄、准、有力），穿透表面，只点出最本质的那一点

**Prompt 改动**
1. JSON 模板：从"描述这次觉察"改成"**一句话点出最本质的那一点**"
2. 新增规则："summary 是「一击」不是「清单」"——绝不要并列罗列
3. 新增规则："summary 要具体到能让用户一眼认领"（"对，就是这个"）——不用套话
4. 新增规则："summary 宁短勿长"——只有1句原话时，绝不比原话长
5. 新增规则："sources 和 summary 分工不同"——sources 可以宽，summary 不需要逐句覆盖

**设计理念**
- 同一次对话里多个看似不同的觉察点，大概率来自同一情绪、共同底色
- AI 的任务不是逐条归纳，而是穿透到最深层的那个共同主题
- 一句有力的洞察 > 完整覆盖所有细节

**心理学依据（额外讨论）**
同一句话可以同时属于"觉察"和"接纳"两个类别——真正的接纳以觉察为前提，这两层有时同时发生，不矛盾（符合 ACT 等心理学框架）

**效果对比示例**
| | 安利机会那条觉察 |
|---|---|
| 之前 | "你注意到面对安利机会时内心犹豫，也觉察到这激起了健康意识，同时发现对AI回应尴尬" |
| 之后 | "你发现自己容易被外面的机会牵着走，心里其实没那么笃定" |

sources 仍然保留那 3 句原话供追溯，但 summary 只给最本质的一击。

**涉及的概念（小白笔记）**
- **一击 vs 清单**：一击=一句话直击本质；清单=逐条罗列要点
- **穿透 vs 归纳**：穿透=找到表面之下的共同主题；归纳=把几句话概括总结

### 2026-06-05 · 澄清"觉察"的定义：必须是关于"内在状态"，不是"外部知识" ✅ 已实现

**背景 / 问题**
- 测试发现 AI 把"我理解不同行业的营销差异"也识别为"觉察"
- 用户质疑：觉察不是应该指对自己内在的认知吗？展示专业知识也算吗？
- 核心混淆：把"我知道的事（外部知识）"误判为"我看见的我（自我觉察）"

**决定**
- 明确觉察的心理学定义：**觉察 = 对自己内在状态（情绪、模式、心理）的意识**
- 在 Prompt 中增加"不算觉察"的反例，划清边界：
  - ❌ 对外部情况的分析："我知道面试官在意XX"（分析他人）
  - ❌ 专业知识展示："我理解行业差异"（专业洞察）
  - ❌ 事实陈述："我有XX经验"（能力陈述）
  - ❌ 策略思考："我可以在面试中提出XX"（行动计划）
  - ✅ 真正的觉察："我发现自己因为怕失败才拖延"（内在动机）

**为什么重要**
- 产品核心价值是帮助用户"看见自己"（自我觉察），不是"展示能力"
- 混淆会导致：
  1. 用户以为"说出专业知识"就是成长 → 偏离了自我探索的初衷
  2. 识别结果变成"能力展示大会" → 失去了心理陪伴的本质
  3. 降低了真正觉察的价值 → 用户分不清"懂道理"和"看见自己"的区别

**相关测试发现**
- 测试"思考模式"时发现：不开启反而识别更准确
  - 不开启：6个亮点（但有2个是误判的"专业知识"）
  - 开启：4个亮点（遗漏了一些，但没有明显误判）
- 最终决定：不开启思考模式 + 澄清"觉察"定义 = 最优方案

**涉及概念**
- **觉察（Awareness）**：心理学概念，指对自己内在状态的意识
- **元认知（Metacognition）**：对自己思维过程的认知，是觉察的一种
- **自我觉察 vs 外部认知**：前者是"看见我"，后者是"知道事"

### 2026-06-03 · 正向亮点识别：觉察、接纳、行动三板块 ✅ 已实现

**背景 / 问题**
- 只识别负面模式会导致用户只看到问题，打击积极性："我怎么这么差"。
- 与产品"温柔、接纳、陪伴"的定位矛盾——只展示负面变成了"批判者"。
- 用户说："用户对话了几次之后，他总是看到的是跟负面模式相关的，会不会就不想用了？"

**决定**
- 新增正向亮点识别功能，分三个板块：
  - 🔍 **觉察**（认知层面）：看见自己的模式/情绪/想法
  - 💚 **接纳**（情感层面）：对自己温柔、不批判
  - 🚀 **行动**（行为层面）：已经做了、或此刻明确要去做
- 与负面模式不同：**正向亮点1次就记录**，不需要"≥3次才算模式"。
- 理由：正向行为本身就值得鼓励，"你启动了1次"比"你拖延了1次"更值得记录。

**展示方式**
- 模式地图页：三个板块折叠显示，点击查看详情（方案A）
  ```
  ✨ 你在一点点靠近
  
  🔍 觉察 (5次) →
  💚 接纳 (2次) →
  🚀 行动 (3次) →
  ```
- 点击后弹出详情卡片：emoji + 统计 + 按日期分组的原话（最近10条）+ 反思语
- 反思语（底部尾巴）：
  - 觉察："你在一点点看清自己"
  - 接纳："你在学会对自己温柔"
  - 行动："你在一点点靠近"

**为什么这个顺序**
- 觉察 → 接纳 → 行动 是心理学上的递进关系（ACT疗法）：
  1. 先看见问题（觉察）
  2. 接受当下的状态，不批判（接纳）
  3. 朝价值方向行动（行动）

**"行动"的判断标准（基于语义理解，不是关键词匹配）**

本质定义：用户表达"此刻就要做/正在做/刚做完"的具体事情

判断方法（三个维度）：
1. **时间性**：是此刻/马上/刚完成，还是将来/假设？
   - 不要只看有没有"现在"这个词，要理解整句话的语义
   - "打算去睡觉了"（"了"表示马上）→ 是行动
   - "打算以后早起"（"以后"表示将来）→ 不是行动

2. **确定性**：是决定/承诺，还是想法/期待？
   - "我去做" → 决定 → 是行动
   - "希望能做" → 期待 → 不是行动

3. **具体性**：是可执行的动作，还是抽象概念？
   - "去睡觉" → 具体 → 是行动
   - "变得更好" → 抽象 → 不是行动

✅ 算行动的例子：
- "我去做了"、"那我先去歇一下"、"我现在打算去..."
- "打算去睡觉了"、"准备去跑步了"（"了"表示即将发生）
- "睡觉去了"（倒装不影响）

❌ 不算行动的例子：
- "希望能通过...来..."（期待，不是决定）
- "...是有好处的"（观念，不是行动）
- "我打算以后每天早起"（未来习惯，不是此刻行动）
- "找个时间学英语"（不确定的将来）

**处理行动覆盖和取消**：
如果一次对话中有多个行动，需判断关系：
- 转折取消："打算睡觉...但想起要交报告，还是先写吧" → 只记录"写报告"
- 顺序执行："先去洗澡，然后写报告" → 两个都记录
- 只是犹豫："不知道该睡觉还是写报告..." → 不记录（没有决定）

**"行动"vs"行动意图"**
- 最终保持"行动"这个名字，不改成"行动意图"。
- 理由：在对话语境中，"说出来"本身就是一种行动（承诺）；"行动意图"太学术化，破坏并列关系。
- 未来可扩展："已完成记录"功能（check-in），与当前的"行动"（对话中的推动）分开。

**为什么用AI语义识别**
- 不是关键词匹配，是理解语义。
- 给AI的是"判断标准 + 反例"，不是死板的关键词列表。
- AI会理解同义表达："我意识到"="我发现"（都是觉察）。

**涉及的概念（小白笔记）**
- **ACT（接纳承诺疗法）**：心理学疗法，强调觉察→接纳→行动的递进过程。
- **语义识别 vs 关键词匹配**：前者理解意思，后者只看词面。

**现状 / 下一步**
- ✅ 已实现：AI识别prompt、数据存储结构、模式地图展示、详情卡片。
- ✅ 多次迭代收紧"行动"识别标准，从宽松到极严格。
- 历史数据需要用新标准重新识别（控制台脚本）。

### 2026-06-02 · 诚实记忆漏洞修复：没记忆时也要明确告知 AI ✅ 已实现

**背景 / 问题**
- 记忆系统召回到历史片段时，会注入"背景记忆 + 使用规则"→ AI 知道自己该守什么边界。
- **但没召回到时，什么都不注入**（返回 `null`，静默）→ AI 没有任何"你对这个人一无所知"的提醒 → 在"老朋友"人设压力下，AI 顺口编"我们之前聊过熬夜"。
- 红线只在"有记忆"时激活，"没记忆"那一侧是个空档。

**决定**
- `buildMemoryContext()` **永远返回一段指令**，不再返回 `null`：
  - 召回到 → 给出真实原话 + 使用规则（不串故事、贴原话、不加细节）
  - 没召回到 → 明确告知"你没有任何关于这位用户的过往记录，绝对不要声称我们聊过"
- 系统提示词红线从"被问到才承认"升级为**禁止主动声称**"我们之前聊过/上次你说过/我记得你提到"，除非确实在背景记忆里。

**为什么**
- **结构性漏洞 > 模型不听话**：AI 偶尔不听规矩是正常的，但"没有规矩"本身才是根本问题。补上这段指令，至少在结构上把口子堵了。
- **信任是这个产品的命**：用户一旦发现 AI 在编造记忆，产品的"理想的自己"人设就崩了。

**涉及的概念（小白笔记）**
- **静默副作用**：代码里"什么都不做"有时候比"做错了"更难发现，因为没有报错信号。

**现状 / 下一步**
- ✅ 已实现：`buildMemoryContext()` 改为永远返回字符串；记忆用法提示词收紧（禁止串故事、贴原话不许加细节）。
- 根本解法是语义召回（见下方 Worker 决策），关键词召回永远存在"词面碰运气"的误判风险。

### 2026-06-02 · 记忆系统升级路径决策：关键词是过渡，语义召回是终点 〔部分待实现〕

**背景 / 问题**
- 现有的关键词召回有根本性天花板：只认词面，"健身"≠"锻炼"，"小灵感"和"之前问过"这种泛词一碰就把不相干的旧话捞出来，捞到后 AI 还会把零散片段串成"看起来有因果的故事"。

**决定——三种方案的取舍：**

| 方案 | 结论 | 理由 |
|------|------|------|
| **关键词召回**（现在） | 继续用，但不深投 | 是过渡方案，最终会被替换 |
| **语义召回（embedding）** | ✅ 正确升级方向，等 Worker 一起做 | 按"意思"找而不是按"词面"碰；检索到后依然端原话，保住诚实红线 |
| **摘要记忆** | ❌ 直接淘汰 | 天生要改写、概括 → 最容易编造，与"诚实的记忆"红线直接打架 |

**现在做（将来语义召回也复用）：**
- 日期锚点、记忆用法措辞收紧（禁止串故事、贴原话）——这是"记忆的出口逻辑"，不管检索引擎怎么换都用得上。
- 临时收紧关键词门槛（泛词过滤 + 至少命中 2 个词）——权宜之计，换语义召回后删掉。

**等 Worker 建好再做：**
- 语义召回需要把文字转成向量（embedding），这一步需要调模型 API → 需要后端 → 搭 Worker 顺道做。

**为什么**
- **召回的"出口"不变**：`buildMemoryContext` 永远是"返回几条片段 + 使用指令"，将来换语义召回只是把里头的检索方式换掉，外面的提示词全复用。
- **不深投即将被替换的方案**：精雕关键词匹配是在给将来要扔的东西加班。

**涉及的概念（小白笔记）**
- **语义召回 / embedding（向量检索）**：把每句话转成一串数字（向量），用"数字距离"来衡量"意思有多像"，不依赖关键词重合。
- **摘要记忆**：每次对话后让 AI 概括"关于这个用户我知道什么"并更新一段文字——问题是 AI 会改写原话，引入不存在的细节。

**现状 / 下一步**
- ✅ 日期锚点、用法措辞、临时收紧已实现。
- 〔待实现〕语义召回：等 Cloudflare Worker 建好后，用 Cloudflare 自带 AI 模型做 embedding，本地存向量、本地算相似度。

**背景 / 问题**
- 担心对话太长会导致：① token 超限；② 系统提示词权重衰减；③ 用户提到"很多次对话之前的事"找不到。

**决定**
- **当前对话不限制长度**：一次对话通常不会超过 token 上限（一次对话 30 轮≈60 条消息，远低于限制）。
- **历史对话全量保存**：所有对话完整保存在 `localStorage` 的 `allConversations`。
- **跨对话记忆靠关键词召回**：已有的 `recallFromHistory()` 函数会自动从历史中检索相关内容，临时注入当前请求。
- **不使用滑动窗口**：除非实际遇到 token 超限问题，否则先不加复杂度。

**为什么**
- **MVP 够用原则**：现有机制已经能处理记忆问题，不要过度设计。
- **用户体验优先**：保留完整对话 > 节省 token。用户说"我上次提到的那个事"，AI 能回忆起来比省几分钱重要。
- **关键词召回机制已在工作**：代码里已实现（第 1164-1258 行），自动从历史中搜索相关片段。

**涉及的概念（小白笔记）**
- **滑动窗口（sliding window）**：只保留最近 N 条消息，旧的自动删除，用于控制 token 数量。
- **关键词召回（keyword recall）**：从历史记录中搜索包含相似关键词的内容，临时注入当前对话。
- **Token 限制**：API 对单次请求的文本长度有上限，超过会报错。

**现状 / 下一步**
- ✅ 已实现：`recallFromHistory()` 和 `buildMemoryContext()` 已在代码中工作。
- 策略：先观察实际使用情况，如果真的遇到 token 超限，再考虑滑动窗口或对话压缩。

**决定**
- 这段改成「**镜子**」：不下结论、不给建议，只把用户**自己跨时间说过的原话**并排摆出来，让 TA 自己看见重复。
- 结尾加一句「**苏格拉底式追问**」，但**只能问、不能劝**：
  - ✅ "你注意到了吗？""像同一个你吗？""上次这么说，是什么时候？"

- 计数别用冷冰冰的"出现 N 次"，**报时间**（"5/21、5/31 各一次"）更像还原。

**为什么**
- 产品核心价值是「**让无意识的重复变得可见**」——让人「看见」靠的是他自己的原话被并排摆出来那一刻，不是一句温柔总结。
- 镜子**对识别误差免疫**：就算模式识别识别错了，最多只是「把你说的话摆出来」，不会像解读那样把错误放大（比如把"今晚吃啥"上升成"能量消耗、行动瘫痪"的尴尬）。
- 跟对话的 SYSTEM_PROMPT 人设一致（"相信我自己说出来的答案比你告诉我的更有力量"）。

**涉及的概念（小白笔记）**
- **模板 vs 个性化**：模板=所有人一个样；个性化=用这个人自己的数据生成。
- **人设一致性**：产品里所有「AI 说的话」要像同一个人，对话克制、卡片却说教，就是人设裂开。

**现状 / 下一步**

### 2026-05-31 · 「模式」的定义门槛：1 次 / 2 次 / 3 次三档 〔待实现〕

**背景 / 问题**
- 导航栏中间叫「模式地图」，但「模式」这个词本身意味着「重复」。现在代码里 **2 次就叫「模式」**并显示，名不副实。

**决定**——三档：

| 次数 | 叫什么 | 上不上地图 | 卡片怎么说 |
|---|---|---|---|
| 1 次 | 一次觉察 | ❌ 不上，只待在日记 | 不盖「模式」的章 |
| 2 次 | 苗头 · 观察中 | ✅ 上，但**不叫「模式」**、标「观察中」 | 谦虚："这是第 2 次了"；尾巴向前看："再出现一次就值得看看了" |
| ≥3 次 | **X 模式** | ✅ 正式叫「模式」 | 打**跨时间原话对照**牌；尾巴向回看："三次了，你注意到了吗？" |

**为什么**
- 老话：「**一次偶然，两次巧合，三次成模式**」。
- 跟自己**已有的判断一致**：日记页早就故意「单次不显示标签」（代码注释写了"单次对话的标签不代表模式"）。
- 现有代码**一个对话最多记一条**该模式（按时间戳去重），所以"3 次 = 3 个不同对话都冒出来"，门槛有含金量，不是"一次吐槽说了 3 遍"。
- 保留「2 次=观察中」是为了**救冷启动**：门槛提到 3，新用户地图会更空（又回到"看不见痕迹"的留存问题），「观察中」让地图别空着，还制造"差一次就坐实"的期待，勾人回来。

**涉及的概念（小白笔记）**
- **冷启动 (cold start)**：新用户刚来、数据还很少时，产品价值兑现不出来的尴尬期。
- **去重 / 计数语义**：先想清楚"出现 1 次"到底指什么，数字才有意义。

**现状 / 下一步**

**尾巴（追问句）—— 已选定「AI 版」**（用户 2026-05-31 拍板）
- **只用于「模式」档（≥3 次）**。「观察中」档尾巴就是固定那句"如果再出现一次就值得看看了"，**不调 AI**（才 2 次，凑不出有意义的共同点，也要保持谦虚）。所以 API 只为坐实的模式触发，更省。
- 做法：AI 读懂这条模式下的原话后，指出它们之间的**共同点**再追问——例"三次都是在事情结束之后——你注意到了吗？"。这句是真正戳人的地方，零成本版给不了。

- **必须缓存**（否则每次打开卡片都转圈 1~3 秒 + 重复花钱）。聪明做法=**搭便车**：每次「结束对话」本来就调 API 做模式识别，等某模式**新攒够一次**时顺手重算这条模式的反映、存进 localStorage → 打开卡片永远 0 等待，只在"真的又多一次"时才花钱。
- **失败兜底**：API 失败时退回一句通用追问句（备 3-4 句轮换："像同一个你吗？""上次这么说，是什么时候？""你注意到了吗？"），别让卡片空着。

## 二、放量前待办（MVP 验证通过后再碰，现在先不做）

### 待办1：分享图生成功能
洞察卡片保存成图片，方便用户分享到社交网络

- **方向一（推荐）**：洞察文字为主角
  - 元素：引号框 + 洞察文字 + 动物emoji + "而此刻，你正在路上" + 二维码
  - 原因：洞察内容是产品独特价值，比身份标签更有传播力
- **方向二**：身份卡片
  - 元素："5年后的[昵称]" + 动物 + 特质 + 理想场景描述
  - 原因：强化用户身份认同，适合首次分享
- **为什么现在不做**：①需要前端 canvas 绘图或调用图片生成服务，开发成本高；②展览现场用户未必会主动分享；③优先验证产品核心价值（对话 + 洞察），分享是传播手段，放量后再做
- **什么时候变重要**：MVP 数据显示用户对洞察卡片有强烈兴趣（截图、询问如何保存），或需要通过分享机制扩大传播
- **技术方案**：使用 html2canvas 或 Cloudflare Workers 调用图片生成 API

### 待办2：「理想的我」回答一致性问题
当用户问 AI"你现在在做什么"时，AI 会从历史召回片段 + 自由创意中填答，导致不同对话答案不一致（一次说手作饰品，另一次说产品顾问）。
  - **为什么现在不改**：①触发这个问题的用户是少数（需要主动探索角色且跨对话比较）；②MVP 阶段展览用户不会在展期内同一账号用两次以上；③修了让答案变单薄（因为 profile 只有一句场景描述），体验可能更差。
  - **什么时候变重要**：留存数据差，或用户反馈"角色前后矛盾"，说明有足够比例用户在跨对话探索这个角色。
  - **已分析的解法**：
    - 解法A（改引导流程）：让用户在 onboarding 时描述更具体的未来生活（典型一天是什么样？），AI 有了更细的素材，答案就更稳定。
    - 解法B（生成并存储未来生活描述）：onboarding 完成后调一次 API，基于 profile 生成一段 200 字左右的"未来的我的生活"，存入 localStorage，每次对话注入作为稳定锚点。这是最根本的解法，但需要额外的 API 调用和存储逻辑。
  - **现阶段决定**：不改，接受"不同对话可能有不同细节"作为长期产品的自然状态，等有了用户数据再评估优先级。

- **模式加「时间维度」**：用「最近 30 天内 ≥3 次」替代「历史累计 ≥3 次」。理由：上周冒 3 次（正在发生）和半年零散冒 3 次（早过去了）分量完全不同，前者才贴合"此刻卡在哪 / 此刻被推动"的定位。
- ~~「我看到的你」是否升级成 AI 现场生成~~ → **已在 2026-05-31 决定提前做**：模式档（≥3 次）的尾巴用 AI 生成共同点观察（见上方决策）。成本可忽略，配套缓存即可。此条不再是"放量待办"。

## 三、成本 & 延展性备忘

- 当前对话和模式识别都调 **DeepSeek API**：每次「结束对话」会调一次做模式识别。
- **历史记忆召回是纯本地关键词检索，不调 API**（已实现，零成本）——这是个好的省钱设计，新功能能本地做就别上 API。
- 任何「改成 AI 生成」的优化，都要配套**缓存**，否则每次打开都烧一次 token。

## 四、概念小词典（边做边学，按需追加）

- **模式 (pattern)**：反复出现才叫模式；一次是偶然，两次是巧合，三次才算。
- **冷启动 (cold start)**：新用户数据少、产品价值还没法兑现的早期阶段。
- **模板 vs 个性化**：模板=所有人看到同一句；个性化=用这个人自己的数据生成。
- **人设一致性**：产品里所有 AI 说的话要像同一个人，语气/原则不能自相矛盾。
- **缓存 (cache)**：算一次就存下来，下次直接取，省时间省钱。
- **system prompt**：给 AI 设定身份和说话规矩的那段「人设说明书」。
- **语义召回 / embedding（向量检索）**：把每句话转成一串数字（向量），用"数字距离"衡量"意思有多像"，不依赖关键词，"健身"和"锻炼"能被认为是同一个意思。
- **摘要记忆**：让 AI 概括"关于这个用户我知道什么"并滚动更新——问题是 AI 会改写原话、引入不存在的细节，与"诚实的记忆"红线冲突，本产品不用。
- **Cloudflare Worker**：运行在云端的轻量后端代码，用来藏 API key（前端只调 Worker，key 不进浏览器）、也可以顺道做 embedding。
- **静默副作用**：代码里"什么都不做"有时比"做错了"更难发现，因为没有报错信号（本产品的"没记忆时不注入→AI乱编"就是这种）。
- **草稿（draft）**：用户没有主动保存、但系统自动暂存的对话，存在 localStorage，下次打开可以续聊或自动收尾。
